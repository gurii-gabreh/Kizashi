## 2. アプリコンセプト（新方針）

### アプリ名：きざし（英語表記：Kizashi）

「兆し（前兆現象）に気づき、届ける」という機能面と、「助かってほしい」という祈るような思いの両方を込めた名前。

**一言で言うと：**
土砂災害の現場で、待機する家族・関係者の情報伝達の遅れと二次災害リスクを減らし、司令官の負担を軽減する、Web完結・無料の現場情報共有アプリ。

### 開発の原点（動機）
Guriiさんの親戚が土砂災害に遭い、消息不明の状態に。ご本人も徹夜で現場に立ち会った。当時「ここでは起きない」という思い込み（正常性バイアス）があり、逃げ遅れにつながった。現場では、同じ質問を家族に何度も聞き取る非効率、報告が人づてで遅れる・誤って伝わる、指示待ちで手が空く時間が長いといった、アナログな運用の課題を痛感した。

---

## 3. ターゲット

**主役は「救助する側」ではなく「現場で待機する被災者家族・関係者」。**

理由：Yahoo!防災速報（8,000万DL）、NHK防災、消防団専用アプリ「S.A.F.E.」等、「一般向け事前警戒」と「対応組織向け」のアプリは既に存在するが、「災害発生後、現場で待つ家族」向けのアプリは検索した範囲で明確な先行事例が見つからなかった。

## 4. 機能設計

### 【メイン】核心機能

1. **危険エリア／待機可能エリアの可視化**
   東京都「土砂災害警戒区域等マップ」データを用い、特別警戒区域・警戒区域・比較的安全な場所を地図上に色分け表示。

2. **二次災害アラート**
   気象庁「土砂キキクル」（10分ごと更新、5段階の危険度分布）と現場の位置情報を照合し、危険度が上昇したら現場にいる全員（救助関係者・待機家族含む）へ即座に通知。「現場にいる人自身の安全確保」が目的（救助判断のためではない）。

3. **事前問診フォーム（重複聞き取りの解消）**
   家族が待機中にスマホで、行方不明者の情報を事前入力。現場の指揮者・関係者はいつでも確認でき、同じ質問を繰り返さずに済む。内閣府の検討資料でも「同じ質問を繰り返し聞かれる」ことが公式課題として明記されている。項目は警察の「行方不明者届」で標準的に聴取される内容に準拠し、独自の追加項目は設けない。

   - 基本情報：氏名、年齢、性別、最後に確認された場所・時刻
   - 身体的特徴：身長、体格、髪型・髪の色、眼鏡の有無、その他の特徴（任意）
   - 服装：最後に確認された時の服装
   - 捜索・救助に直接必要な情報のみ：現在服用中の薬、アレルギー、歩行・移動の可否（病歴を包括的に聞くことはしない）
   - 写真：最近の写真（任意、最大1〜2枚）

   **本フォームは警察の公式システムを置き換えるものではなく、届出時に慌てず答えられるようにする「事前整理・下書き」という位置づけ。** 病歴等は「要配慮個人情報」に該当するため、捜索に直接必要な最小限の項目に絞り、現場ルームごとに暗号化保存、事案終了後は一定期間（例：30日）で自動削除する。

4. **報告・記録のデジタル共有**
   「誰が」「どこを」「いつ確認したか」をアプリ上で記録し、関係者間でリアルタイム共有。口頭・紙伝達による遅延・誤伝達を防ぐ。

5. **前兆現象 共有モード**
   国土交通省・首相官邸が公式に定める前兆現象チェックリスト（がけの割れ目、湧き水、川の急な濁り・水位低下、山鳴り等）を現場の誰でもワンタップで報告。位置情報・時刻付きで即座に関係者全員へ共有。「予測」ではなく「公式チェックリストに基づく目撃情報の共有」と位置づける。

6. **危機感を伝えるUX設計（正常性バイアス対策）**
   - 抽象的な警報でなく「あなたのいる場所は特別警戒区域内です」等、具体的な場所・状況を名指しする通知
   - 前兆現象の報告があった場合、「〇〇さんの近くで報告がありました」という"誰かからの呼びかけ"の形で通知（「逃げなきゃコール」の考え方を援用）
   - 周囲の避難状況を共有し、同調性バイアスを行動を促す方向に活用
   - 通知を出しすぎない（気象庁も課題としてきた「オオカミ少年効果」を避けるため、精度の高い時のみ発信）

### 【時間があれば追加】

- 家の見取り図の簡易可視化（国土地理院データ活用）
- 過去の土砂災害事例の参照機能
- 待機時間中のタスク整理・共有掲示板

## 5. 絶対にやらないこと（人命に関わるため、明確に除外）

| 除外機能 | 理由 |
|---|---|
| 助かる見込み時間・生存確率の提示 | トリアージ・救助優先順位の判断は消防・自衛隊等の専門領域。未検証のAIが提示すれば誤判断のリスクが極めて高い |
| 重機の自動手配 | 契約・費用・法的責任が伴い、アプリが実行することは現実的に不可能 |
| 指揮官不要の意思決定代替 | 災害対策基本法上、指揮権は市町村長・都道府県知事・消防・自衛隊に帰属。個人アプリが代替することは法的に成立しない |
| 独自の線状降水帯予測アルゴリズム開発 | 気象庁・JAXA・大学等の協定参加機関限定データが必要。個人開発の範囲を超える国家プロジェクト級の研究領域 |

## 6-1. GeoJSON実データ検証結果（2026-07-18）

国土数値情報ダウンロードサイトから、東京都の土砂災害警戒区域データ（令和4年度版、A33-22_13_GML.zip、約21MB）を実際に取得し、`prototype/doshasai-prototype.html` に統合して検証した。

**検証環境の制約：** この検証を行ったClaude Codeセッションは、組織のネットワークポリシーにより nlftp.mlit.go.jp・www.jma.go.jp・d-keikai.metro.tokyo.lg.jp・cyberjapandata.gsi.go.jp（国土地理院タイル）等、外部の政府・都サイトへの直接アクセスが一切ブロックされていた。そのため、データのダウンロードはユーザーが手元の環境で行い、zipファイルをセッションにアップロードする形で進めた。国土地理院タイルの表示確認も同じ理由でこのセッション内では実施できていない（コード上は正しく設定されているが、実際にタイル画像が表示されるかは別環境での確認が必要）。

### 判明した事実

1. **GeoJSON形式は変換不要で同梱されていた。** zip内に GML（`A33-22_13.xml`）・Shapefile（`Shape/`）に加え `A33-22_13Polygon.geojson`（34MB、29,641件）が最初から含まれており、GML→GeoJSON変換の実装は不要だった。
2. **座標系はJGD2011だが、GeoJSON版はすでにWGS84（EPSG:4326）で出力されていた。** メタデータ（`KS-META-A33-22_13.xml`）上、原本のGML座標系は `JGD2011 / (B, L)` だが、同梱のGeoJSONはRFC 7946の慣例に従いWGS84で書き出し済みで、Leaflet.jsへの追加の座標変換は不要だった。変換スクリプト（`tools/convert_ksj_a33.py`）にはJGD2011等の場合の再投影処理も念のため実装してあるが、今回のデータでは発火しなかった。
3. **属性列名はKSJ内部タグ名がそのまま `A33_001`〜`A33_008` の連番で出力されていた。** 元GMLの `ksj:cop`（現象区分）・`ksj:coz`（区域区分）・`ksj:prc`（都道府県コード）・`ksj:znn`（区域番号）・`ksj:znm`（区域名称）・`ksj:ads`（所在地）・`ksj:pad`（指定年月日）・`ksj:cus`（特別警戒未指定フラグ）の順に `A33_001`〜`A33_008` へ機械的にマッピングされていることを実データで確認した。
   - **要検証（未確定）：** `A33_001`（現象区分）の値1/2/3、`A33_002`（区域区分）の値1/2 が何を意味するかのコードリストが、データ本体にもメタデータにも同梱されていなかった。国交省の「製品仕様書 第2.0版」PDFで正式な対応を確認する必要がある（このセッションからはnlftp.mlit.go.jpへのアクセスがブロックされておりPDFを確認できなかった）。`tools/convert_ksj_a33.py` では暫定的に「1=急傾斜地の崩壊/2=土石流/3=地すべり」「1=警戒区域/2=特別警戒区域」という一般的なKSJの並び順を採用しているが、確定情報ではない。
   - 市区町村コード（例：13101〜13123の5桁コード）に相当する列は存在せず、23区への絞り込みは `A33_006`（所在地の住所文字列）に区名が含まれるかどうかで行った。
4. **ファイルサイズと表示速度：** 東京都全域（29,641件、山間部・島嶼部含む）をそのまま座標簡略化（許容誤差0.00003度≒約3m）した場合でも約17MBあり、そのままではプロトタイプの表示に不向きだった。23区の住所を含むものだけに絞り込むと1,818件・約1.6MB、同じ許容誤差で簡略化すると約880KBまで縮小できた。この880KBの23区データを `prototype/data/tokyo_23wards_sabo_zones.geojson` としてプロトタイプに組み込み、Playwright（ヘッドレスChromium）でfetch読み込み・ポリゴン描画・クリックで属性表示、の一連の動作を確認した（国土地理院タイル自体はこのセッションのネットワーク制限で読み込み確認できていない）。
5. **prototypeの実装：** `doshasai-prototype.html` は、`data/tokyo_23wards_sabo_zones.geojson` をfetchで読み込み、成功すれば実データを、file://で直接開くなどfetchが失敗する環境ではサンプルデータにフォールバックする構成にした。実データ配信にはHTTP(S)サーバー経由での配信が必須（file://だとブラウザのCORS制限でfetchがブロックされる）。

### 変換ツール

`tools/convert_ksj_a33.py` にGML/Shapefile/GeoJSONいずれの入力にも対応する変換スクリプトを用意した。`--inspect` で列名・CRS・件数を確認したうえで、`--wards-only`（23区絞り込み）・`--tolerance`（座標簡略化）を指定して変換する。詳細は `tools/README.md` を参照。

## 6-1-2. 気象庁防災情報XML検証結果（2026-07-19）

ユーザーから提供された気象庁公式PDF2点（`docs/reference/` に配置）をもとに検証した。

1. **公式URLを確認。** 「気象庁防災情報XMLフォーマット情報提供ページ」は
   http://xml.kishou.go.jp/index.html 。このセッションから www.jma.go.jp・
   xml.kishou.go.jp への接続は組織ネットワークポリシーでブロックされており
   直接アクセスして実配信データを取得することはできなかったが、PDF内の記載で
   URL自体は正しいことを確認した。
2. **フォーマット構造を確認。** JMAXML Ver.1.3（2022年12月9日版）は
   管理部（Control）・ヘッダ部（Head）・内容部（Body）の3部構成。警報・注意報は
   `Information type="気象警報・注意報（市町村等）"` の下に `Item`（`Kind`＝警報種別・
   `Condition`＝現象種別、`Areas`＞`Area`＝市区町村名・JISコード）という構造で
   表現される。土砂災害に関連する警報は `Kind/Condition` に「土砂災害」という
   文字列が入る形で判別できる。市区町村コードはJIS X0402の5桁（都道府県コード
   ２桁＋市区町村コード３桁）に、市町村内の細分区域を示す2桁を付加した7桁。
   東京都は先頭2桁が「13」。
3. **加工・編集の許容範囲を確認。** 「XML形式電文のご利用にあたっての留意事項」
   （令和2年9月1日付）に、「公開ＸＭＬ電文に含まれる特定地域を対象として、その
   地域に関係する要素・属性のみの情報を選別して切り出し、ひとつの電文として
   再構築する場合」は編集・加工してよい例として明記されており、例として
   「東京地方23区西部」の切り出しが挙げられている。本アプリが行う予定の
   「東京都・区市町村単位への絞り込み表示」はこの許容例に直接合致する。一方、
   「個々の要素を利用者側で独自の予報に編集する」ことは明確に禁止されており、
   企画整理.md セクション5・9の「独自予報として発信せず、公式発表の表示・転載に
   とどめる」という方針は、この留意事項と整合していることを確認できた。
4. **パース処理を検証。** `tools/jma-xml-poc/` に、Cloudflare Workers上でも動く
   純JS実装（`fast-xml-parser`）を使ったパーサーのプロトタイプを作成した。
   仕様書の記述例をもとに作成した検証用サンプルXML（`sample_warning.xml`。
   実際の配信データではない）に対し、東京都（JISコード先頭"13"）の警報のみを
   抽出し、「土砂災害」に関連するものを判別する処理が正しく動くことを確認した。
5. **未検証のまま残る点：** Cloudflare Workersから実際に `xml.kishou.go.jp` の
   フィードへ定期的にHTTPリクエストを送り、実配信XMLを取得できるかどうかは、
   このセッションのネットワーク制限のため検証できていない。ネットワーク制限の
   ない環境（実際のCloudflare Workers環境等）で改めて確認する必要がある。

## 6-1-5. LINE Messaging API検証結果（2026-07-19）

LINE公式サイト（`https://www.lycbiz.com/jp/service/line-official-account/plan/`。
このセッションからはブロックされておりユーザーに内容を確認していただいた）で、
LINE公式アカウントの料金プランを確認した。

| プラン | 月額固定費 | 無料メッセージ | 追加メッセージ |
|---|---|---|---|
| コミュニケーションプラン（無料） | ¥0 | **200通/月** | 不可 |
| ライトプラン | ¥5,000（税別） | 5,000通/月 | 不可 |
| スタンダードプラン | ¥15,000（税別） | 30,000通/月 | 〜¥3/通（税別） |

**懸念：月200通は現場ルームの通知用途には少なすぎる可能性が高い。** 1つの現場
ルームに複数人（家族・現場関係者）が参加し、前兆現象の報告・気象警報の変化等で
数回プッシュ通知を送るだけでも、1インシデントあたり数十通に達しうる。無料枠の
200通は同時期に発生する複数の現場・複数の利用シーンを想定すると早期に枯渇する
リスクがある。なお、ここでいう「無料メッセージ」がプッシュ配信（Messaging API
の送信）のみを指すのか、応答メッセージ（Webhookへの返信）も含むのかは、
lycbiz.comのこのページからは確認できておらず、別途LINE Developersの技術文書
（`developers.line.biz`、このセッションからはブロックされアクセス不可）での
確認が必要。

**方針：** 企画整理.md セクション7で元々「第一候補：ブラウザのWeb Push通知、
現実的な代替：LINE Messaging API」としていた優先順位を維持し、むしろこの検証
結果によりWeb Push通知（無料・上限なし）を主、LINEは無料枠の範囲に収まる
小規模な利用（例：1現場・少人数向けの補助的な通知）に限定する方向を明確にする。
無料枠を超える見込みが立った場合は、費用完全無料の制約（セクション9参照）に
反するため、LINE通知機能自体をスコープから外すか、送信対象を絞る設計にする
必要がある。

## 6-2. 将来の多災害対応（プレゼンでの将来展望として言及。今回のエントリー・実装対象には含めない）

アプリのアーキテクチャ（現場ルーム、事前問診フォーム、危険エリア可視化、報告共有、通知の仕組み）は災害種別を問わず汎用的に設計しているため、将来的に地震・火災にも拡張可能。東京都都市整備局「地震に関する地域危険度測定調査」（都内5,192町丁目、建物倒壊危険度・火災危険度・総合危険度を5段階評価、約5年ごと更新）という東京都公式データが既に存在する。

**ただし今回のエントリーでは土砂災害に一点特化する。** 理由：
- Guriiさんの実体験（動機となるストーリー）は土砂災害に基づくものであり、地震・火災には直接転用できない
- 前兆現象共有モードは国交省が公式に定めた土砂災害の前兆現象チェックリストに基づいており安全に実装できるが、地震には科学的に確立された前兆現象の公式基準が存在しない（緊急地震速報はP波検知後の警報であり「予知」ではない）。火災も同様に統一的な公式チェックリストは確認できなかった。この機能は地震・火災には転用しない
- エントリー概要文・根拠データ・プレゼンのストーリーはすべて土砂災害の実体験と東京都の土砂災害データに一貫して基づけており、これを分散させると説得力が落ちる

将来展望としては「本アプリのアーキテクチャは東京都の地域危険度データ（建物倒壊・火災）にも将来的に対応拡張が可能」という一文をプレゼンに添える程度に留める。

## 7. 技術構成（詳細）

### 全体アーキテクチャ
```
[ユーザー（家族・現場関係者）] → スマホブラウザ
        ↓
[フロントエンド：Web完結、インストール不要]
        ↓
[Cloudflare Workers（バックエンド処理）]
        ↓
   ┌────┴────┬─────────┐
[東京都データ] [気象庁データ] [ユーザー入力データ]
（危険区域）    （警報・注意報）  （問診・報告・前兆現象）
```

### フロントエンド
- HTML/CSS/JavaScript（軽量、フレームワーク最小限）
- 地図：Leaflet.js（無料）＋国土地理院タイル（無料・APIキー不要。Google Mapsは大量アクセス時の課金リスクがあるため不採用）
- モバイルファースト設計。まずWebブラウザで完結させ、将来的にPWA化してiPhone対応を段階的に強化

### 東京都データの取り込み
- 「土砂災害警戒区域等マップ」をGeoJSON形式（国土数値情報経由）で取得し、Leaflet.js上にポリゴン表示（特別警戒区域＝赤、警戒区域＝黄）

### 気象庁データの取り込み（正直な設計）
- 警報発表状況：気象庁防災情報XML（無料・登録不要）をCloudflare Workers経由で定期取得。「気象業務法」への配慮から、独自予報は行わず公式発表の表示・転載にとどめる
- 詳細な危険度分布（キキクル）：独自にタイルデータを取得・加工するのではなく、気象庁公式ページを埋め込み表示（iframe）またはリンク提示とし、法令リスクを回避

### バックエンド・データ保存
- Cloudflare Workers + D1（無料枠、SQLデータベース）。問診フォームや前兆現象報告など構造化データの検索・管理に適するため、KVよりD1を採用
- テーブル例：incidents（現場ID）、family_intake（事前問診）、reports（確認記録）、precursor_signs（前兆現象報告）

### アクセス管理
- 複雑なログイン機能は作らず、現場ごとに発行するユニークコード（例：6桁）またはQRコードで「現場ルーム」に参加する方式とし、開発工数を削減

### リアルタイム性
- MVPでは10〜30秒ごとのポーリング方式を採用。時間があればCloudflare Durable Objects（無料枠）でより即時性の高い通知に拡張

### 通知機能
- 第一候補：ブラウザのWeb Push通知
- 現実的な代替：LINE Messaging API（現場のLINEグループへ自動投稿。高齢の家族がいても扱いやすい）

### 開発優先順位（技術面）
```
【最優先】
①東京都データによる危険エリア地図表示
②現場ルームの作成・参加（コード発行）
③前兆現象の報告・共有
④事前問診フォーム（身体的特徴含む）

【次点】
⑤気象庁警報XMLの自動取り込み
⑥LINE通知連携
⑦危機感を伝えるUX文言の作り込み

【将来展望（プレゼンで語るのみ）】
⑧キキクル詳細データとの高度な連携
⑨完全リアルタイム化（Durable Objects/WebSocket）
⑩iPhoneネイティブアプリ化
```

## 8. 既存競合との比較（正直な立ち位置）

| サービス | 対象者 | 位置づけ |
|---|---|---|
| Yahoo!防災速報（8,000万DL）、NHKニュース・防災 | 一般市民（事前の備え） | 競合するが対象者が異なる |
| 消防団専用アプリ「S.A.F.E.」 | 消防団員（活動サポート） | 現場情報共有という発想は近いが対象が異なる |
| SIP4D（内閣府・防災科研、国家プロジェクト） | 災害対応機関間の情報連携 | 目指す方向は同じだが、規模も対象もまったく異なる。個人開発はこの"隙間"を埋める位置づけ |
| 各種避難所アセスメント調査票のデジタル化（内閣府検討中） | 避難所の被災者 | 「同じ質問の繰り返し」問題は内閣府も認識しているが、土砂災害現場での家族向け実装は未確認 |
| 災害用伝言ダイヤル171／伝言板／J-anpi | 被災地にいる本人が自ら無事を発信できる場合 | **前提が根本的に異なる。** 本人が発信不能（行方不明・要救助）な状況は対象外であり、Guriiさんのアプリはまさにこの空白を埋める |
| ANPIC・トヨクモ「安否確認サービス2」等（企業向け） | 企業が従業員の安否を一斉確認 | 家族単位・個人の捜索現場の情報共有には非対応 |
| People Locator／ReUnite（米国NLM開発） | 災害時の家族による行方不明者情報共有（海外） | **骨格が最も近い先行事例。** 画像・位置情報・音声メモ対応。2015年ヒンドゥークシュ地震で実際の救助につながった実績あり。ただし日本語・日本の行政データには非対応 |
| Google Person Finder（2010年ハイチ地震で開発） | 災害時の安否情報横断検索（オープンソース、海外） | 同上。オープンソースである点はGuriiさんの方針と一致するが、日本の行政データとの連携はない |

**正直な結論：** 「一般向け警報」領域はYahoo!・NHKに勝てない。「安否確認」領域は171・J-anpi等が強いが、これらは「本人が発信できる」前提であり、行方不明・要救助という「本人が発信できない」状況は対象外。「現場で待つ家族」「本人発信不能時の情報整理」という切り口は、国内では明確な競合が見つからなかった。海外にPeople Locator/ReUniteという骨格の近い先行事例はあるが、日本の行政データ・現場運用課題への特化度で差別化できる。

## 9. リスク管理（法的・倫理的な安全設計）

- 生存可能性・救助優先順位に関わる判断は一切行わない
- 前兆現象は「予測」ではなく「国交省公式チェックリストに基づく目撃情報の共有」として位置づける
- 通知は過剰にせず、精度の高い時のみ発信（オオカミ少年効果の回避）
- 指揮権を代替する表現・機能は持たない
- 気象庁データは「気象業務法」に配慮し、独自予報として発信せず、公式発表の表示・転載にとどめる
- 事前問診フォームの身体的特徴・病歴・写真は「要配慮個人情報」に該当するため、警察届出の標準項目に絞り、暗号化保存・事案終了後の自動削除・現場ルームコードによるアクセス制限を行う
